# Проверка На Двух Физических Устройствах

> **HISTORICAL (2026-09-30):** this document describes the removed legacy prototype (static-ECDH session layer, `STANDARD_AEAD`, v1 invitations, reciprocal pairing, device approval states), deleted by DEC-021. It is kept for history and audit context only and does not describe current code. Current design: [Protocol v2](PROTOCOL_V2.md).

## Назначение И Граница Доказательств

**Проверенная база репозитория:** `ae09872615d119f5c77e960704c83606485f16f9`

Этот документ описывает ручной debug-сценарий для двух физических Android-устройств в одной
локальной сети. Он не является отчётом о выполненном тесте. Результат считается доказательством
только после записи точного commit, устройств, API level, команд и фактических pass/fail/skip
результатов.

Приложение не готово для реальной чувствительной переписки:

- рабочие чаты используют прототип `SimplifiedSessionManager`, а не проверенные PQXDH и
  Double Ratchet;
- первая связь разрешается в warning-only состоянии без независимой проверки личности;
- HTTP в локальной сети не защищает транспорт и метаданные;
- фоновые повторы не гарантируют своевременную доставку;
- официальный Signal-путь выключен; `PARANOIA_C4_AEAD` полностью удалён из кода (2026-09-27);
- независимый аудит не выполнен.

Используйте только одноразовые тестовые профили, сообщения и доверенную тестовую Wi-Fi сеть.

## Предварительные Условия

Нужно подготовить:

- доверенный ноутбук с JDK 17, Android SDK, ADB и Node.js 20+;
- два Android-устройства API 31+ с включённой USB-отладкой для установки APK;
- одну локальную Wi-Fi сеть, доступную ноутбуку и обоим телефонам;
- чистые одноразовые профили без реальной переписки;
- текущий commit и пустой журнал результатов.

Перед началом запишите:

```text
Commit:
Ноутбук / ОС:
Node.js:
JDK:
Телефон A / API:
Телефон B / API:
Wi-Fi сеть:
Relay URL:
Дата и время:
```

## 1. Автоматизированная Проверка Перед Ручным Сценарием

Из корня репозитория:

```bash
cd android-app
./gradlew :app:assembleDebug
./gradlew :app:lintDebug :core:signal-protocol:testDebugUnitTest :core:signalstore:test test
```

Relay:

```bash
cd android-app/server/relay
node --test
```

Не называйте команды пройденными без записанного вывода. Ошибка любой обязательной проверки
должна быть зафиксирована до продолжения ручного QA.

## 2. Запуск Локального Relay

```bash
cd android-app/server/relay
node src/server.mjs
```

По умолчанию сервер слушает `0.0.0.0:8787`. Проверка с ноутбука:

```bash
curl http://127.0.0.1:8787/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

Текущий минимальный сервер хранит в памяти:

- `messageId`;
- `queueId`;
- непрозрачный ciphertext envelope;
- время истечения.

Он ограничивает тело запроса и максимальный TTL, но не является production-сервисом. В
штатном процессе сервер не должен журналировать тела, ciphertext, ключи, nonce или queue ID.
Это не заменяет проверку reverse proxy, hosting-платформы, системных журналов и сети.

## 3. LAN-Адрес Ноутбука

На macOS для стандартного Wi-Fi интерфейса:

```bash
ipconfig getifaddr en0
```

Если результат пустой:

```bash
networksetup -listallhardwareports
```

Используйте адрес активного Wi-Fi интерфейса. Пример:

```text
http://192.168.1.45:8787
```

Правила:

- `127.0.0.1` и `localhost` на телефоне указывают на сам телефон;
- `0.0.0.0` — адрес привязки сервера, а не URL клиента;
- `10.0.2.2` относится к Android Emulator, а не к физическому телефону;
- локальный firewall ноутбука должен разрешать входящие подключения Node к порту `8787`;
- не открывайте debug relay в публичный интернет.

`adb reverse tcp:8787 tcp:8787` подходит для одного подключённого телефона, но не является
двухтелефонным Wi-Fi-сценарием.

## 4. Сборка И Установка

Из `android-app`:

```bash
./gradlew :app:assembleDebug
adb -s <serial-A> install -r app/build/outputs/apk/debug/app-debug.apk
adb -s <serial-B> install -r app/build/outputs/apk/debug/app-debug.apk
```

Убедитесь, что установлена debug-сборка текущего commit. Release-сборка должна отклонять
cleartext HTTP и не подходит для этого LAN-сценария.

## 5. Настройка Одноразовых Профилей И Relay

На каждом телефоне:

1. Создайте отдельный тестовый локальный профиль.
2. Откройте `Настройки` → `Сервер доставки`.
3. Введите один и тот же LAN URL ноутбука.
4. Нажмите `Сохранить сервер`.
5. Нажмите `Проверить сервер доставки`.
6. Зафиксируйте результат `Сервер доступен` или точную ошибку.
7. Откройте `Готовность к тесту переписки` после выбора проверяемой переписки, когда она
   появится.

HTTP разрешён только для debug LAN QA. Он раскрывает IP, время, queue ID, размеры и частоту
запросов и не защищает от задержки, удаления, повторной выдачи или отказа в обслуживании.

## 6. Взаимный Импорт Приглашений

Приглашение содержит receive queue создателя. Один QR-код не создаёт двусторонний маршрут.

1. На A откройте `Добавить контакт` и покажите приглашение A.
2. На B отсканируйте приглашение A, задайте локальное имя и импортируйте.
3. На B покажите собственное приглашение B.
4. На A отсканируйте приглашение B, задайте локальное имя и импортируйте.
5. На обоих телефонах подтвердите завершение обоих импортов.
6. Проверьте, что pairing показывает `Готово к переписке`.

`Готово к переписке` означает пригодный двусторонний адрес для текущего primary-only
маршрута. Это не означает, что личность проверена.

## 7. Проверка Warning-Only Первого Контакта

До сравнения safety number проверьте принятую onboarding-политику:

- контакт имеет `VerificationStatus.UNVERIFIED`;
- соответствующее основное устройство имеет
  `DeviceApprovalStatus.PRIMARY_UNVERIFIED`;
- интерфейс постоянно предупреждает, что личность не проверена;
- состояние не называется `VERIFIED` и не предлагается для важной переписки;
- тестовое сообщение разрешено к отправке на основное устройство.

Отправьте короткое бессодержательное тестовое сообщение A → B. Не используйте секреты или
реальные персональные данные.

Если отправка в этом состоянии блокируется, зафиксируйте это как расхождение с принятой
warning-only политикой. Если предупреждение отсутствует, это также дефект.

## 8. Полный Цикл Доставки И Receipt

Для сообщения A → B:

1. На A зафиксируйте начальный статус `Ожидает синхронизации` или непосредственный переход.
2. После принятия relay проверьте `Отправлено на сервер доставки` (`SENT`).
3. На B нажмите `Синхронизировать сейчас`, если сообщение ещё не появилось.
4. На B проверьте один экземпляр сообщения со статусом `Получено` (`RECEIVED`).
5. Получатель должен поставить encrypted delivery receipt в тот же delivery pipeline.
6. На A выполните синхронизацию при необходимости.
7. Проверьте переход исходного сообщения A в `Доставлено` (`DELIVERED`).

`DELIVERED` означает, что A аутентифицировал receipt о принятии, расшифровании и durable
storage приложением B. Это не означает, что человек прочитал сообщение. Read receipts не
реализованы.

Повторите полный цикл для B → A.

## 9. Независимая Проверка Личности

После проверки warning-only поведения:

1. На обоих устройствах откройте безопасность контакта.
2. Сравните safety number или verification QR через доверенный или независимый канал.
3. При полном совпадении явно отметьте контакт и основное устройство как проверенные.
4. Убедитесь, что состояние стало `VERIFIED` и unverified-warning исчез только после этого.
5. Отправьте ещё по одному тестовому сообщению в обе стороны и повторите receipt-проверку.

Несовпадение QR или safety number нельзя обходить ручным подтверждением.

## 10. Retry После Недоступности Relay

1. Остановите relay.
2. Отправьте новое тестовое сообщение A → B.
3. Зафиксируйте `PENDING`/`FAILED`, attempt count и следующий retry в диагностике.
4. Не очищайте данные и не создавайте новое сообщение с тем же текстом.
5. Запустите relay снова.
6. Дождитесь WorkManager либо нажмите `Синхронизировать сейчас`.
7. Проверьте, что relay принимает сохранённый ciphertext без второго отображаемого сообщения.
8. На B синхронизируйте и проверьте ровно один принятый экземпляр.
9. На A обработайте receipt и проверьте `DELIVERED`.

WorkManager выполняется по возможности и может быть задержан Android. Отсутствие быстрого
повтора не доказывает потерю durable retry state; фиксируйте время и используйте ручную
синхронизацию для диагностического разделения.

## 11. Duplicate И Restart

Для расширенного ручного QA:

- повторная выдача аутентифицированного envelope не должна создавать второе сообщение;
- receipt-дубликат не должен повторно менять состояние;
- после перезапуска приложения принятый replay marker и session counter должны сохраняться;
- relay blob должен удаляться только после durable acceptance или распознавания
  аутентифицированного дубликата;
- неаутентифицированный или повреждённый blob не должен отображаться как сообщение и может
  оставаться в очереди до TTL или внешнего удаления.

Ручное создание tampered envelope не является обязательным для обычного тестового дня; для
этого предпочтительны автоматизированные тесты.

## 12. Device-State Ограничения

Текущий runtime не реализует cryptographic multi-device fan-out. Он выбирает только основное
устройство.

Проверьте, если сценарий подготовлен безопасно:

- `PRIMARY_UNVERIFIED` и `VERIFIED` разрешены как primary target;
- `PENDING_APPROVAL`, device `KEY_CHANGED`, `REVOKED` и отсутствие primary блокируют;
- contact `VerificationStatus.KEY_CHANGED` блокирует интерактивную отправку;
- secondary device не выбирается молча.

Полное fail-closed поведение для `VerificationStatus.UNKNOWN`, повреждённых persisted values,
migration 1 → 2, restart и queued retry ещё не считается подтверждённым. Не представляйте
этот пункт как уже пройденную гарантию.

## 13. Диагностика И Безопасный Сбор

На каждом телефоне откройте `Настройки` → `Диагностика доставки` и сохраните только
санитизированный отчёт.

Допустимы:

- статусы, счётчики и timestamps;
- короткие fingerprints queue ID;
- pairing/device/worker status;
- last error;
- модель устройства и API level.

Недопустимы:

- текст сообщений;
- invitation payload целиком;
- private/session keys;
- nonce;
- ciphertext;
- полный queue ID;
- реальные персональные данные.

Для Logcat используйте `LOGCAT_QA.md`.

## 14. Завершение Теста

1. Остановите relay.
2. Сохраните отчёт с commit и фактическими результатами.
3. Используйте debug `Сбросить тестовые данные` только для одноразового QA-состояния.
4. Помните, что reset сохраняет выбранный Relay URL и не является forensic erase.
5. Не утверждайте, что локальный reset удалил все relay copies: blobs могут существовать до
   receipt/delete, TTL или поведения внешнего relay.

## Что Relay Всё Ещё Видит

- IP-адреса клиентов и время запросов;
- queue identifiers;
- размеры и частоту envelopes;
- факт использования одного relay двумя устройствами.

AEAD должна отклонять несанкционированное изменение содержимого, но не предотвращает traffic
analysis, задержку, удаление, withholding, replay, flooding или denial of service.

## Критерии Успешного Результата

Результат можно назвать успешным только если записаны:

- точный commit и среда;
- результаты обязательных команд;
- relay health на обоих телефонах;
- взаимный импорт приглашений;
- видимое warning-only состояние до verification;
- A → B и B → A с различением `SENT`, `RECEIVED` и `DELIVERED`;
- authenticated receipts;
- retry recovery без duplicate plaintext;
- независимая verification и корректный переход в `VERIFIED`;
- все ошибки и пропуски.
