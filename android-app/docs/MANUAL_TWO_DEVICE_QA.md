# Ручная Проверка Двух Физических Устройств

## Назначение

Этот чеклист предназначен для debug-теста доставки между двумя физическими
Android-устройствами в одной Wi-Fi сети. Если второго телефона нет, используйте
подтверждённую альтернативу: физический Android-телефон + Android Emulator через
локальный relay на ноутбуке, описанную в
[PHONE_EMULATOR_PUBLIC_RELAY_QA.md](PHONE_EMULATOR_PUBLIC_RELAY_QA.md).
Это проверка MVP, а не подтверждение production security: активные чаты используют
`SimplifiedSessionManager`, Signal-backed sessions и `PARANOIA_C4_AEAD` выключены,
а LAN HTTP relay предназначен только для разработки.

## Перед Началом

На ноутбуке из каталога проекта:

```bash
cd android-app/server/relay
node --test
node src/server.mjs
```

Relay должен слушать `0.0.0.0:8787`. Проверьте его локально:

```bash
curl http://127.0.0.1:8787/health
```

На macOS обычно получить Wi-Fi IP можно так:

```bash
ipconfig getifaddr en0
```

Если адрес не найден, выполните `networksetup -listallhardwareports` и используйте
активный Wi-Fi интерфейс. Для IP `192.168.1.45` URL тестового relay будет
`http://192.168.1.45:8787`.

`127.0.0.1` и `localhost` на реальном телефоне означают сам телефон, а не
ноутбук. `0.0.0.0` нужен серверу для прослушивания интерфейсов, но не является
адресом, к которому должен подключаться телефон. `127.0.0.1` подходит только
вместе с `adb reverse` для USB-теста одного устройства. Два телефона в Wi-Fi
должны использовать LAN IP ноутбука. Адрес эмулятора `http://10.0.2.2:8787`
не используется на физических устройствах.

Подтверждённый рабочий сценарий без Cloudflare Tunnel:

- физический телефон использует `http://<LAN_IP_ноутбука>:8787`;
- Android Emulator использует `http://10.0.2.2:8787`;
- URL разные, но оба указывают на один и тот же локальный Node relay на ноутбуке;
- сообщения успешно отправляются и принимаются в обе стороны: телефон -> эмулятор
  и эмулятор -> телефон.

Stability QA 2026-05-29 для этого сценария также прошёл: проверены 5 сообщений
телефон -> эмулятор, 5 сообщений эмулятор -> телефон, закрытие и повторное
открытие приложения, ручная синхронизация, остановка relay, pending/retry,
повторный запуск relay, повторная синхронизация и отсутствие дублей. Sanitized
logcat физического телефона не показал `FATAL EXCEPTION`, `AndroidRuntime`, ANR,
ошибок WorkManager, Room, Keystore или QR scanner для `app.securemessenger`.

## Confirmed QA: automatic retry and delivery receipts

Ручной QA phone + Android Emulator через локальный Node relay подтвердил текущую
семантику доставки:

- обычные сообщения доставляются в обе стороны;
- после durable accept входящего сообщения второе устройство отправляет encrypted
  delivery receipt обратно отправителю;
- статус исходящего сообщения меняется с `Отправлено на сервер доставки` на
  `Доставлено` только после получения receipt;
- receipt может приходить с небольшой нормальной задержкой, потому что это
  отдельное обратное control message;
- при выключенном relay новое исходящее сообщение получает статус
  `Ожидает синхронизации`;
- после восстановления relay background sync / WorkManager сам отправил
  pending/retry сообщения без обязательного нажатия `Синхронизировать сейчас`;
- после receipt статус retry-сообщения стал `Доставлено`;
- дубли сообщений не появились;
- receipt не отображается как обычное сообщение;
- диагностика доставки показала корректные technical events и понятные статусы.

Кнопка `Синхронизировать сейчас` остаётся полезной для ручной QA-проверки и
ускорения сценариев, но успешный тест подтвердил, что best-effort background sync
может восстановить доставку автоматически после возвращения relay.

`Доставлено` означает, что устройство получателя приняло, расшифровало и
сохранило сообщение, а затем отправило delivery receipt. Это не read receipt:
прочтение пользователем в MVP не отслеживается.

## Confirmed QA: VPS relay and reboot

Дополнительно пройден QA через Ubuntu 24.04 LTS VPS:

- временный debug-only URL: `http://194.87.226.46`;
- Caddy принимает HTTP на порту 80 и проксирует на loopback relay
  `127.0.0.1:8787`;
- Node relay работает через enabled systemd service `secure-messenger-relay`;
- `caddy.service` также enabled;
- UFW закрывает прямой внешний доступ к `8787/tcp`;
- телефон и Android Emulator успешно отправили и приняли сообщения в обе стороны;
- после остановки relay сообщения получили `Ожидает синхронизации`;
- после восстановления relay WorkManager/background sync автоматически повторил
  отправку примерно через 6-7 секунд;
- receipt вернулся, статус изменился на `Доставлено`, дубли не появились;
- после reboot VPS Caddy и relay автоматически поднялись.

Публичный HTTP по IP допустим только как временная debug/QA-проверка. Для release
и production необходимы домен и HTTPS. VPS relay остаётся недоверенным transport:
сервер видит IP, timing, queue metadata и приблизительные размеры сообщений.

Cloudflare Tunnel или другой публичный HTTPS relay остаётся optional future/public-network
вариантом, когда клиенты не могут достучаться до одного локального relay.

## Настройка Устройств

1. Установите одну debug APK на устройства A и B и создайте на каждом отдельный локальный профиль.
2. На каждом устройстве откройте `Настройки` и нажмите на всю строку `English`,
   затем на всю строку `Russian` / `Русский`. Заголовки должны переключаться сразу,
   а выбранный язык должен сохраниться после перезапуска приложения.
3. Убедитесь, что выбор срабатывает по тексту, по свободной части строки и по кружку
   radio option для языка. `Paranoia C4` должна оставаться недоступной.
4. На обоих устройствах откройте `Настройки` -> `Сервер доставки`.
5. Введите один LAN URL ноутбука и сохраните его.
6. Убедитесь, что показано предупреждение о debug-only HTTP relay.
7. Нажмите `Проверить сервер доставки` и получите статус `Сервер доступен`.
8. Откройте `Диагностика доставки`: там должен появиться health status, но не текст сообщения и не полный queue ID.

## Preflight Перед Отправкой

После настройки обоих телефонов и выбора проверяемой переписки:

1. Откройте `Настройки` -> `Готовность к тесту переписки`.
2. Проверьте URL, последнюю проверку сервера, контакт, статус подключения,
   состояние основного устройства, pending/failed counts и статус фоновой синхронизации.
3. Нажмите `Проверить готовность к переписке`.
4. До отправки ожидайте результат `Готово к тесту переписки`.

Preflight должен остановить сценарий с понятной причиной, если URL не указан,
введён `127.0.0.1` / `localhost` / `0.0.0.0` на реальном телефоне, relay
недоступен, QR-подключение не завершено, устройство блокирует отправку либо
осталась очередь повторной отправки.

## Двусторонний QR Pairing

1. A показывает своё приглашение в `Добавить контакт`; B сканирует и импортирует его.
2. B показывает своё приглашение; A сканирует и импортирует его.
   Если камера не считывает QR с экрана эмулятора или телефона, нажмите
   `Скопировать код приглашения` на одном устройстве и вставьте код через
   `Вставить код приглашения` на другом.
3. При каждом нажатии `Сканировать QR-код` проверьте, что scanner открывается
   вертикально. Поворот телефона не должен переводить scanner в landscape.
4. Также откройте QR-проверку контакта в разделе безопасности и проверьте тот же portrait-режим.
5. На обоих устройствах откройте разговор и подтвердите, что выполнен импорт обоих QR-кодов.
6. Статус должен измениться с инструкции о втором QR-коде на `Готово к переписке.`
7. По доверенному каналу сравните контрольные коды безопасности и отметьте устройства проверенными.

Подтверждение взаимного QR в UI является записью о выполненном пользователем шаге,
а не автоматической криптографической аттестацией второго телефона.

Если импортирован только один QR-код, это ожидаемое ограничение текущей
privacy-модели MVP: приложение не создаёт неизвестные контакты автоматически, не
использует глобальный user ID и не загружает адресную книгу. Получатель начнёт
видеть переписку только после явного импорта приглашения отправителя. В таком
состоянии UI должен показывать `Ожидает обратное приглашение` и объяснение:
`Для двусторонней переписки второй пользователь тоже должен импортировать ваше приглашение`.

## Доставка A -> B И B -> A

1. На A отправьте короткое тестовое сообщение B.
2. На B нажмите `Синхронизировать сейчас`, если fetch не выполнился автоматически.
3. Проверьте появление сообщения и событие `INCOMING_ACCEPTED` в диагностике B.
4. На B отправьте ответ A и повторите проверку на A.
5. В отчёте допустимы статусы, счётчики, время и значения вида `sha256:...`; полного queue ID, payload, nonce, ключей или ciphertext быть не должно.

Статус `Отправлено на сервер доставки` означает только, что relay принял
зашифрованный blob. Статус `Доставлено` появляется только после encrypted delivery
receipt от устройства получателя. В этом MVP `Доставлено` означает, что receiving
device приняло, расшифровало и сохранило сообщение, а затем отправило
подтверждение доставки. Это не означает, что пользователь прочитал сообщение:
read receipts не реализованы.

## Retry После Остановки Relay

1. Остановите процесс relay на ноутбуке.
2. Отправьте новое тестовое сообщение.
3. Сообщение должно остаться в durable outgoing queue со статусом
   `Ожидает синхронизации`, а не потеряться окончательно.
4. В диагностике отправителя проверьте увеличение failed/retry count и событие `OUTGOING_RETRY_SCHEDULED`.
5. Снова запустите relay и проверьте `/health`.
6. Подождите background sync / WorkManager. В подтверждённом QA pending/retry
   сообщения отправились автоматически после восстановления relay.
7. Если нужно ускорить проверку или зафиксировать ручное действие, нажмите
   `Синхронизировать сейчас` на отправителе. Manual sync должен сразу повторить
   retryable failed messages, даже если автоматический `nextRetryAt` ещё не наступил.
8. Нажмите `Синхронизировать сейчас` на получателе, если входящий fetch не произошёл автоматически.
9. Проверьте `OUTGOING_RETRY_STARTED`, `OUTGOING_RETRY_SUCCEEDED`,
   `OUTGOING_SENT`, `INCOMING_ACCEPTED`, `DELIVERY_RECEIPT_QUEUED`,
   `DELIVERY_RECEIPT_SENT`, `DELIVERY_RECEIPT_RECEIVED` и `DELIVERY_STATUS_UPDATED`.
10. Повторная синхронизация не должна создавать дубль plaintext-сообщения.

WorkManager выполняет best-effort синхронизацию; энергосбережение Android может
задержать её, поэтому ручная кнопка остаётся контрольным действием QA, а не
обязательным шагом успешной доставки.

## Сброс Между Сценариями

В debug-сборке в `Настройки` доступна кнопка `Сбросить тестовые данные`. После
подтверждения она удаляет локальный профиль, контакты, сообщения, сессии,
replay markers, pending/retry очередь, записи отключённого Signal-spike,
диагностику и технический журнал; приложение возвращается к первому запуску.
URL сервера доставки намеренно сохраняется для повторения LAN-теста. В release
этой QA-кнопки нет.

## Logcat QA

Для воспроизведения сбоя на одном выбранном телефоне из `android-app` запустите:

```bash
./scripts/start_qa_logcat.sh
# воспроизведите проблему и нажмите Ctrl-C
./scripts/analyze_qa_logcat.sh qa-logcat.txt
```

Подробности и правило использования только тестовых сообщений приведены в
[LOGCAT_QA.md](LOGCAT_QA.md). Файл `qa-logcat.txt` локальный, маскируемый и не
должен попадать в git или публичные вложения.

## Duplicate Suppression

Для штатного ручного сценария relay удаляет принятое сообщение после durable local
save, поэтому дубль не должен появляться. Если тестовый harness повторно подаёт тот
же authenticated envelope, в UI не должно появиться второе plaintext-сообщение, а
журнал может показать `INCOMING_DUPLICATE_SUPPRESSED`. Не модифицируйте ciphertext
вручную для пользовательского теста.

## Блокировка Устройств

В разделе безопасности контакта проверьте следующие состояния:

- `Ожидает проверки`: отправка блокируется с причиной pending approval.
- `Отозвано`: отправка блокируется с причиной revoked.
- `Ключ изменён`: отправка блокируется с причиной key changed.
- Отсутствующее основное устройство: отправка блокируется с причиной missing primary device.

Ни одно новое или изменившееся устройство не должно получить автоматическое доверие.

## Если Тест Не Прошёл

Запишите без сообщения и без секретов:

- модель устройства и версию Android;
- версию debug APK/commit hash;
- Relay URL и время проверки `/health`;
- диагностический отчёт из приложения;
- результат блока `Готовность к тесту переписки`;
- sanitized summary из `./scripts/analyze_qa_logcat.sh qa-logcat.txt`;
- вывод терминала relay без содержимого пакетов и секретов;
- направление доставки (A -> B или B -> A);
- видимые статусы pending/failed/next retry и technical event codes;
- был ли relay остановлен, перезапущен или недоступен через firewall.

Не прикладывайте тексты сообщений, QR invitation payload, ключи, nonce, полные
queue IDs или encrypted blob contents.
